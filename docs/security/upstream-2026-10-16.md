# Upstream Portainer review — 16 October 2026

This is a targeted source comparison, not a penetration test or a complete vulnerability audit. It compares Vessel's `b534dd2236db588ddce594fd9660636406aa9c11` plus the current native-extension working tree with upstream's published [2.45.1](https://github.com/portainer/portainer/releases/tag/2.45.1) and [2.45.2](https://github.com/portainer/portainer/releases/tag/2.45.2). Read-only `git ls-remote` on 16 October confirmed `2.45.2` at `6981dc67c177ab64d12bd74e1ccc02abf19bb057`, `develop` at `be20b574172a27251fd8648cefe1b810a8dad6a5`, and `master` at `c0ee5b67d8c01d461346efbde239654a68b3dde5`. The merge base with 2.45.2 is `4d3b5ceb99068d18ef43902cbe8e59954128315f`, the 2.45.0 version-bump commit. The published patch release is the relevant security comparison; `develop` alone does not contain all its changes.

No upstream branch was merged. Vessel's API/datastore compatibility identity remains 2.45.0; a security backport does not require changing that identity. These are inherited missing fixes, not regressions shown to have been introduced by the extension work.

## Applied in this prerelease work

### Resource-control authorization

[Upstream 09382f14](https://github.com/portainer/portainer/commit/09382f14a7095e3d2c31c538058cc0de509fad60) closes a real condition error in `backend-src/api/http/security/authorization.go`. An authenticated non-administrator who already has write access to a resource control could submit their own user plus two or more foreign write-access teams. The old condition rejected exactly one team, then returned true for the matching user before checking team membership. The resource-control update handler actually calls this predicate before persistence, so the affected path is reachable.

The predicate now rejects any mixed write-user/write-team ownership, matching upstream. Vessel's filtering of read-only viewers and its administrator-only sharing rules remain intact. `TestAuthorizedResourceControlUpdate_SelfUserAndMultipleForeignTeamsDenied` was first run against the old predicate and failed, proving the regression test detects the defect. It passes after the fix. The existing read-only-viewer regression remains covered. Fresh verification passed: `go -C backend-src test -race ./api/http/security ./api/http/handler/resourcecontrols` on Go 1.26.6. The first sandboxed full run could not open an httptest localhost socket; the authorized rerun with localhost listeners passed both packages. `git diff --check` also passed for the focused fix and this report.

### gRPC dependency security update

Both the backend and independent SDK previously selected gRPC 1.82.1. [CVE-2026-84304 / GHSA-vp52-pcj8-j9qc](https://github.com/grpc/grpc-go/security/advisories/GHSA-vp52-pcj8-j9qc) affects versions through 1.83.0; 1.83.1 fixes receive-buffer memory exhaustion caused by fragmented HTTP/2 DATA frames. [Upstream Portainer 8d335eed](https://github.com/portainer/portainer/commit/8d335eedd4eb86968273823677bbd37e2e0cf5ec) selects 1.83.2. The prerelease packaging task owns the matching upgrade and its final verification results.

This applies to the new gRPC transport even though mTLS and the Unix socket restrict peers: a malicious peer with an accepted certificate can reach the transport before per-method authorization, and the SDK also receives HTTP/2 data from its configured server. Message-size limits alone do not eliminate per-frame allocation overhead. Version 1.83.2 still declares Go 1.25.0, preserving the SDK minimum. Final dependency versions and test results must be taken from the release verification record, not inferred from this review.

## Compatibility follow-up

- Kubernetes deletion of manifests without an explicit namespace still falls back to `default` in `backend-src/pkg/libkubectl/delete_dynamic.go:136`, rather than the stack namespace. [928224c3](https://github.com/portainer/portainer/commit/928224c3c24dc0a3cb98977b34b31b0c8a1fd129) fixes this; backport before relying on clean removal of non-default-namespace stacks.
- Restricted Docker dashboard volume lookups still use volume name without engine identity in `backend-src/api/uac/volumes.go:26`. [04c4e199](https://github.com/portainer/portainer/commit/04c4e199458709cd5f99a02aa3d6304e2bee1196) fixes the mismatch with stored resource-control keys. Confirm both dashboard counts and ownership filtering when porting it.
- Vessel already has custom GitOps orphan-reference cleanup. Do not overwrite it with upstream's [0a11e101](https://github.com/portainer/portainer/commit/0a11e1018) / [fed73393](https://github.com/portainer/portainer/commit/fed73393b) changes without reconciling source loading, stack deletion transactions and the existing fork tests. Some direct workflow reads still return missing-workflow errors; no broad equivalence claim was established by this review.
- Compose removal already passes its received context to `composeService.Down`, but upstream [a86b6cc6](https://github.com/portainer/portainer/commit/a86b6cc6d1e2ccf841d9482d889bd1057df01b4f) changes the caller's deployment-context propagation too. Inspect the whole call chain before calling it applied.
- Upstream's Swarm list and Kubernetes node-column frontend fixes target its Angular/legacy React layout. Vessel's rewritten frontend must consume the behavioral fix through its current domain/provider interfaces; importing upstream frontend directories would undo architecture boundaries.
- Podman limitations listed in the current upstream release are pre-existing support constraints, including Docker-server/Podman-socket onboarding. They are not evidence of a new Vessel regression. No live Podman, Swarm, Kubernetes or Azure ACI runtime compatibility test was performed in this review. No evidence of an Azure ACI-specific new patch regression was found; absence of a finding is not runtime verification.

## Release assessment

The focused resource-control fix and gRPC patch are appropriate for the extension prerelease. They do not make Vessel equivalent to upstream 2.45.2 security behavior. Keep the prerelease explicitly experimental and record these inherited risks. A production release for untrusted multi-user environments or Kubernetes should wait for the applicable high-priority backports and targeted tests. This review did not authorize or perform a blanket upstream merge, datastore migration, extension infrastructure-write expansion, or a production rollout.
